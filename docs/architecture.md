## 一、需求审查

### 1.1 总体判断

需求定义质量高于绝大多数个人项目：输入输出明确、schema 已有初稿、必须项与可选项划分清晰、验收标准可测量。**总体合理，可以进入开发。** 以下是 6 个需要决策或注意的风险点。

### 1.2 六个关键风险点

**① 文献来源必须先锁定一个。**
"文献检索或本地导入"二选一起步。全文 PDF 有两个坑：版权（多数出版社不允许再分发）和解析复杂度（双栏排版、表格嵌套）。建议 MVP 用 **PubMed 摘要**：免费、官方 API、结构化、无版权问题。全文留作后期增强（PMC 开放获取子集）。
影响：ingestion 模块的复杂度相差 3 倍以上。

**② gold set 是全项目最大的隐性工作量。**
50–100 条 × 每条 15–30 分钟人工核对 ≈ 25–50 小时，约占项目总时间的 1/3。建议**第 2 周就启动**（不要等系统跑通），先定 schema 和判定标准，边标边补。这是文档规定必须由本人主导的部分——AI 只能出模板，不能出答案。

**③ 评测指标分两档落地。**
主文档列了 10 个指标，一次全上会卡死。建议：

| 档 | 指标 | 实现方式 |
|---|---|---|
| v1（第 3–4 周） | 字段 exact match、字段 F1、检索命中率 | 纯确定性计算，无需 LLM judge |
| v2（第 5 周后） | citation accuracy、hallucination rate、faithfulness | LLM-as-a-Judge + 人工抽查 |
| 从第一天起 | 响应时间、token 成本 | 写进日志，零额外成本 |

**④ 评测工具自写为主。**
学习目标要求手写核心流程，而 RAGAS/DeepEval 会把这个学习机会"包掉"。建议：核心指标脚本自己写（约 150 行），RAGAS 只在后期做交叉验证。面试讲"我自己实现了指标计算"远比"我调了 RAGAS"有说服力。

**⑤ 中英混合问题。**
医药文献主体是英文，而提问可能用中文。两个方案：
- (a) 查询预处理时把中文问题转成英文再检索（简单，多一次 LLM 调用）；
- (b) 用多语言 embedding（如 bge-m3）直接跨语言检索。

建议起步用 (a)，后期换 (b) 只需改一个模块。

**⑥ Web UI 不要过早投入。**
Streamlit 一天能搭好，但它不是项目价值所在。先用命令行脚本跑通全流程，UI 放到第 4 周。

### 1.3 MVP 边界（明确砍掉的）

表格抽取、多文献矛盾识别（项目二任务 C 会覆盖）、证据等级评分、PDF 报告输出、文献去重与版本管理——全部不做。MVP = 主文档 6.6 "必须完成"栏，一项不加。

## 二、两种架构方案

### 方案 A：单体流水线（Monolithic Pipeline）

核心思想：系统 = **一条离线索引流水线 + 一条在线问答流水线**，全部是 Python 函数；Streamlit 只是薄壳。

```
【离线 · 建库】（一次性或增量运行）
data/raw/ 文献
   → 解析（PubMed XML / pymupdf）
   → 切分（按句子/段落，附 metadata：PMID、化合物、物种…）
   → embedding（API 或本地模型）
   → FAISS 索引 + SQLite metadata

【在线 · 问答】
用户问题
   → 查询预处理（中→英、实体识别）
   → 混合检索（FAISS 向量 top-20 ∪ BM25 关键词 top-20）
   → rerank → top-5 段落
   → Prompt 组装（段落带编号引用标记）
   → LLM 调用（强制 JSON 输出）
   → pydantic 校验 + 引用回查（引用编号必须真实存在）
   → 结构化 JSON + 可读报告
```

**优点**
1. 每一步都是纯函数，可单测、可断点调试——对学习目标和面试讲解都最有利；
2. 结构与"手写 300–500 行核心流程"（主文档 6.10）完全对应；
3. 零部署、零服务，一台笔记本跑通；
4. 从建库到问答的因果链在代码里一眼可见。

**缺点**
1. 项目二/三复用时只能 import Python 包，无法跨进程/跨机器调用；
2. 无并发、异步、缓存（MVP 单人使用，可接受）；
3. 后期 Agent 化（项目三）需要在流水线外再包一层。

### 方案 B：API 服务化分层

核心思想：RAG 核心作为独立 Python 包，外面套 FastAPI 服务；UI 和未来的评测、Agent 都走 HTTP API。

```
Streamlit UI ──HTTP──▶ FastAPI 服务
                        ├─ POST /ingest    → 离线建库模块
                        ├─ POST /query     → 在线问答模块
                        └─ POST /evaluate  → 评测模块
                              │
                              ▼
                     RAG 核心包（检索/生成/校验）
                              │
                              ▼
                     SQLite + FAISS + LLM API
```

**优点**
1. 一次搭建、三个项目复用：项目二评测调 /evaluate，项目三 Agent 把 /query 当工具调用；
2. 接近生产形态，"FastAPI 服务化"在简历上是加分项；
3. 前后端解耦，换 UI 不动核心。

**缺点**
1. 初期复杂度显著上升：API 设计、双进程、端口、错误码——零工程经验者第一周就可能卡在工程细节而非 RAG 本身；
2. 调试链路变长（bug 可能在 UI、API、核心任何一层）；
3. 与第 1–2 周"跑通最小 RAG"的目标直接冲突。

### 推荐：方案 A 起步，按方案 B 的边界写代码（演进式）

**第 1–5 周用方案 A**，但遵守一条纪律：**核心流水线的每个阶段都是独立模块、纯函数、显式输入输出**。第 6 周后如果项目二/三需要，用 FastAPI 把同样的函数包成服务——因为边界干净，包装成本约半天。

这样既不牺牲起步速度，又不堵死后路，符合主文档"优先保持简单可运行"的原则。

## 三、推荐技术栈

| 层 | 推荐 | 理由 | 备选 |
|---|---|---|---|
| 语言 | Python 3.11+ | AI 生态标准 | 3.12 |
| 环境管理 | venv + pip | Windows 新手最平滑 | uv / conda |
| LLM API | DeepSeek（已确认） | 便宜、国内直连 | 后期评测对比再加模型 |
| Embedding | 本地 BGE，英文语料用 bge-small-en-v1.5（已确认） | 免费、离线 | bge-m3（跨语言检索时） |
| 向量检索 | faiss-cpu | 本地零部署，工业界常用 | Chroma |
| 关键词检索 | rank-bm25 | 纯 Python、轻量 | — |
| Rerank | 第 2 阶段再加（先用 LLM rerank） | 避免早期外部依赖 | Cohere / Jina API |
| 文献获取 | requests + NCBI E-utilities | 官方 REST API，透明可控 | Biopython Entrez |
| 文献解析 | PubMed XML（MVP）；pymupdf（后期全文） | 见 1.2① | GROBID（过重） |
| 数据校验 | pydantic v2 | schema 即代码，输出校验必需 | — |
| 存储 | SQLite + CSV/JSON | 零部署 | PostgreSQL（后期） |
| UI | Streamlit | 数据应用最快路径 | Gradio |
| 评测 | 自写脚本（+ 后期 RAGAS 交叉验证） | 见 1.2④ | DeepEval |
| 测试 | pytest | 标准工具 | — |
